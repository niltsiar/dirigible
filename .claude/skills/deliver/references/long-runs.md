# Long autonomous runs

- Before a loop, write its stop predicate in the first `run.md` (for example, `scripts/wiki.py list next` has no product item); never relax it to stop.
- Take the next goal from `scripts/wiki.py list next --ready`, else the next open item of `docs/requirements/releases.md`, and close each run before the next. The cadence of the steering runs is in `docs/workflow/release-cycle.md`.
- Read `AGENTS.md` from disk at the start of each run.
- At most two runs are in code; beside them, keep 2 or 3 lock-free agents at work (plan, plan gate, review, research, or code with no lock that hands back one bash file); run `scripts/with-lock.sh --builders` to list the building trees. A third tree takes only a lock-free code agent; the `with-lock.sh` cap holds its bash file until a tree ends. A push check, the hooks pass (`scripts/with-lock.sh make test-hooks DIRIGIBLE_HOOKS_ALL=1`), a land, or a mutant runs alone: beside it, run only the code gate reviewers, plan writing, plan gates, other reviews, and doc-only edits in another worktree (no build, no test, no lock-held make). Light read-only work also runs beside it: the Phase 0-2 reading of the next goal, research, run files, built files, and evals except `agent`-type rows. Start an `agent` eval row after it ends. A heavy read-only command (a history scan, a transcript replay, a loop over many files or processes) runs as `WITH_LOCK_NO_CAP=1 scripts/with-lock.sh <command>`: it waits for the build or test of any tree and takes no slot of the cap. Start no build or test in any worktree, and no on-screen check: timing tests fail under load. While a bench or a flake loop runs, start no build, test, commit, or on-screen check; the lock-free agents keep working.
- `.claude/hooks/agent-guard.sh` refuses an agent brief that names a lock step while a push check, the hooks pass, a land, or `make dmg` holds the build lock or waits first for it, or while a stress lane (`scripts/test-stress.sh`, an exclusive window) holds the build lock. A brief of an agent that runs no `with-lock.sh` step carries the line `Build lock: none`, so it passes, and `.claude/hooks/agent-guard.sh` makes no record for it. A `with-lock.sh` call that prints `no lock` also waits while a long holder (a release call, a bench, a mutation pass, a flake loop, or a stress lane) holds the lock, or while a bench marker is live, so its agent starts after that ends.
- Start a release call (a push check, the hooks pass, a land, or `make dmg`) after each agent whose Agent, SendMessage, or delegate_task brief names a lock step hands back, and run lock-free work meanwhile: `.claude/hooks/git-guardrails.sh` refuses the release call while such an agent runs. The end text of a delegate_task child, a completed or failed wait result, or a task_cancel ends its record. For a dead agent, or a child that handed back while the hook still names it, pass RELEASE_PAST=<id> (the comment above the release-wait rule of git-guardrails.sh, rg AGT-152, gives the record, when an agent stops being live, the 90 min upper limit, and the override).
- Time a shell script or a hook test (`make test-hooks HOOK_TESTS=<names>`) that builds no Swift and runs no built binary as `scripts/with-lock.sh --bench-mark <command>` (`references/performance-criteria.md`, A time budget).
- Before the first run of an unattended loop, check the access of Phase 9: `git ls-remote origin`, `gh auth status`, an allow rule for `scripts/land.sh` in `.claude/settings.json` (add it if missing), and a permission mode that allows file edits. If one fails, stack each run branch on the previous one, record it in `run.md`, and land them when the human is back.
- Use only the access that these two commands already have; leave credential stores closed.
- Each run lands green on `main` through its own pull request.
- At a pause, leave each open run at a slice commit or with its working tree as is, and write in `run.md` the next step and each check result, taken from its command output or log, not from memory; make no `wip` commit.
- With `schedule_task` (T3 Code only), end the turn behind a scheduled wake when a wait is over 4 h and nothing runs: a Monitor holds the session for 4 h at most. Call `schedule_task` with a `fixed_time` schedule bound to the thread; for a wait over 24 h, set `weekdays` to the day of the wake; for a wait over 6 days, set the wake again at the first wake. The task ID exists only after the call returns, so then call `update_scheduled_task` to set the prompt to "First call delete_scheduled_task <id>, then continue with <the next step of run.md>", and write the ID in the `run.md` handoff. The wake turn deletes the task first, because a `fixed_time` schedule runs each day. A wait of 4 h or less keeps the re-armed Monitor of `AGENTS.md`.
