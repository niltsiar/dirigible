# Test-first delivery

Make the intended behavior executable before you change production code. The test fails before the change and passes after it.

This repo prefers integration tests over unit tests. An integration test calls a module through its public API, the same way the app calls it, with real inputs: real WAV or FLAC files on disk, real `AVAudioPCMBuffer` data, real session XML. Write a unit test only for a pure function with many edge cases, where an integration test would be slow or hide the failing case.

## Workflow

1. **Understand the behavior.** Identify the intended behavior, the current behavior, the affected path, and the smallest observable result.
2. **Choose the check.** Prefer the integration test target of the module that owns the behavior. Generate audio fixtures in the test (a sine tone, silence, white noise at a known level) instead of committing large binary files.
3. **Write the failing test first.** The test encodes intended behavior, not the current implementation. Assert a literal expected value or an observable effect: a file on disk, a sample count, a level in dBFS within a stated tolerance, a parsed XML element.
4. **Run the new test before the fix.** Confirm that it fails for the intended reason. If it passes, or fails for an unrelated reason, correct the test first.
5. **Make the change.** Write the smallest production change that satisfies the test.
6. **Rerun the test and the full suite.** Run `make test`. Confirm the new test passes and nothing else broke.
7. **Commit in order.** When the change is a bug fix, you can commit the failing test first (`test:`) and the fix on top (`fix:`). For a feature, commit the test and the code together (`feat:`).

## If a failing test is impractical

Some behavior needs hardware: a real microphone, two physical audio interfaces, a permission prompt. Do not silently skip the regression step. Before the change, explain why an automated test is impossible, then pick the closest executable check: an offline render, a virtual device, a script that records five seconds and prints the file facts with `afinfo` or `ffprobe`. Record the manual check in the run ledger so a human can repeat it.

Prefer no new test over a bad test. A bad test mostly tests mocks, encodes implementation details, depends on timing or global state, or would still pass if every function it calls returned nothing.

## Guardrails

- Do not change tests to match a wrong implementation.
- When a test refuses or blocks a user action, also assert that the input of the user stays: the typed text, the open alert, the selection, the clipboard. "The model did not change" alone also passes when the input is lost. If the plan expects the input to be lost, stop and raise it as a plan finding. Do not write that test.
- A test that expects a refusal (a nonzero exit, a thrown error, a refused edit) also asserts its reason: the rule message or the error case. A broken fixture, for example a manifest that does not compile, also fails, so a bare failure passes for the wrong reason.
- Do not weaken existing assertions unless the expected behavior changed, and say why.
- Audio comparisons use a stated tolerance, never exact float equality on processed samples.
- For a writer and reader pair, add one seeded random round-trip test beside the literal tests. Build values through the public edits, write, read, and assert `==`. It tests the claim "every value an edit accepts, the reader accepts".
- A test hook that asserts where work runs (the thread or the actor) is synchronous and sits at the operation itself, for example right after the file read. A hook in a nearby async or nonisolated closure reports the isolation of that closure, so it passes when the operation moves to the main actor. A hook that asserts a priority reads `Task.currentPriority` at the operation, also on a GCD thread. `qos_class_self()` gives only the requested QoS, so it misses the escalation when a caller with a higher priority awaits `task.value` of a detached task.
- A test of a cancel or a stop asserts that no work happens after it (no progress call, no write, no next chunk), not only the end state. An end state such as "cancelled, no file" also passes when a later check stops the work late, so it cannot fail when the earlier guard is removed.
- Give every wait in a test a limit and a failure message: a poll loop, a yield loop, a child process. When a bug or a mutation removes the state that the test waits for, the test must fail, not hang the suite. Compute one deadline for each public call and pass it down to each nested wait: a limit for each step adds up. An expired limit never goes on into the success path. Prove the named failure message with a mutation that forces the miss, and read that message in the output. A shorter outer limit hides the message of an inner wait.
- If a test is flaky, make it deterministic or delete it. Do not retry until green. First run the full suite and the test alone, 15 times each. When only the full suite fails, first read the diff of the slice where the flake first came, with its test helpers, hooks, and gates. Never set a flake aside because the failing test does not touch the changed code: new test code can hold a shared resource. Look for a process-wide resource in the code under test and in the test code: a file descriptor, a lock, a temporary path, an environment variable, the main actor, a serial queue, the threads of the Swift concurrency pool, a user preference of the Mac (for example window tabbing), the key window. Parallel tests share these. A test process has no key window, so `NSApp.sendEvent` can give a synthetic key event to the window of another suite: send it with `NSWindow.sendEvent` to the window of the test. A blocking gate (a semaphore) on a pool thread blocks that thread: in async test code, and in a synchronous hook that a `@concurrent` or detached function calls. When every pool thread waits, the test that opens the gates cannot run. Hold the work at an async seam with `AsyncGate`, and declare a new test seam `async` when async code calls it. `Gate.waitOnce` is `noasync`, so the compiler refuses it only in async code. Pin a user preference that a test depends on before the test opens a window. Delete the test only when the cause is in the test itself. A test moved behind the slow gate, a longer limit, or a smaller fixture is a workaround that weakens a gate. Log it as open in `decisions.tsv`. After the root-cause fix, undo it and prove the undo with the same loop. The proof of a flake fix is a mutation that reproduces the exact failure value of the flake, red on the old code and green on the new code. Commit a flake fix only after the failing command also passes as many times in a row as it took to expose the failure. That loop is a regression check only: at a rate of 1 in 21, an unfixed test passes 20 runs in a row about 38% of the time. A process sample that shows the holder gone is not proof. A change to a shared test helper or to the speed of the suite changes the timing of every test. After such a change, search every suite for the shape it exposes, not only the suites of the run. Do not call a new flake "outside the run" until the same repeat on `main` passes.
- A test that acts on or checks an asynchronous milestone (the writer is attached, the job runs, the progress shows) waits for a signal from the code, or holds the state with a gate. It must not depend on the work being slower than its poll. A faster suite makes such a test fail. A fixed count of `Task.yield()` calls or a sleep is a clock too: each yield waits behind the main-actor jobs of other suites, so a busier suite makes the test fail. Expose the state from the code (for example the count of waiters in a queue) and wait on it with a limit.
- If a wait fails because an actor or a serial queue is busy, name the code that holds it before you change a limit. Find it with a monitor, not more repeat runs, when a red run is a cluster of unrelated wait-limit failures: add a monitor test to the full suite. Every 100 ms it times a pool hop (`await Task.detached {}.value`) and a main-actor hop (`await MainActor.run {}`), and when a hop waits longer than 2 s, a thread outside the pool runs `/usr/bin/sample <pid> 2`. The sample shows the frames of the threads that hold it. Write the holder in `decisions.tsv`. When product code holds it, it is a finding against the plan, not a test fix. When test code holds it (for example file writes in the `init` of a `@MainActor` suite), move that work off the actor first. When no single piece of code holds it and the load of other tests does (GB writes, child processes, disk images), run those tests in a separate process. Keep every limit below the time of one full suite run; a longer limit cannot find a hang. Then make every producer, timer, and watchdog of the test run longer than the wait limit of the step where the test stops it, not its expected time, and end the producer explicitly (for example with a detach). Assert only the property ("before the full duration") with a wide margin, never "promptly". Search for every test that uses the same duration and fix all of them in one commit.

## Final response

- Name the failing-before test and the failure it produced.
- Name the passing-after run (`make test`) and its result.
- If failing-before evidence was impossible, state why and name the closest check you used.
