## Context

Release 2 run 1 (`docs/requirements/releases.md`) adds a customizable toolbar (F93), a window subtitle, banners in place of the transport bar, and a resizable track header panel (F85 part). The user asked for toolbar icons, controls in the title bar, a good look, and no drop in performance, and gave the UI choices to an expert panel (HIG, pro audio, first use and accessibility, visual performance). The run splits in two: run 1a builds the window chrome, and run 1b builds the header panel and the dark lane palette. Research: `docs/research/macos-ui-shell.md`. Run design: `.scratchpads/runs/2026-09-27-ui-shell/design.md` and `ux-decisions.md`.

Probes (MacBook Pro 2018, Intel, macOS 15.7.9, Swift 6.2.4, target macOS 14):

- U3, U4 (research). An `NSHostingController` that is the content controller of a window has `sceneBridgingOptions` `.toolbars` and `.title`. A SwiftUI `.toolbar` then fills the window toolbar with UUID identifiers, and the documentation says that it overwrites an AppKit toolbar.
- U5 (research). A change of the vertical ruler thickness with `tile()` takes 0.058 ms, and the clip view inset follows.
- P1a (`.scratchpads/runs/2026-09-27-ui-shell/probe/output.txt`). The option is 0 before the window takes the controller. With the option `[]`, an AppKit toolbar stays.
- P1b. `NSToolbar.visibleItems` leaves out the items in the overflow menu.
- P1c. With 14 items, 640 pt shows Record, Play, and Stop only; 660 pt also shows the time display. The title length does not change it.
- P2. The in-process accessibility tree of the hosting view has a SwiftUI banner text with its frame.
- P5 (Phase 7, `.scratchpads/runs/2026-09-27-ui-shell/probe/p5-subtitle/`). With `sceneBridgingOptions = []` set after the window takes the controller, the title bar has no subtitle field, and `window.subtitle` keeps its value. Set before, the subtitle draws. A plain window and an `NSHostingView` with `[]` draw it too.

## Decision

**Toolbar.** Each session window has an AppKit `NSToolbar`, style `.unified` with a visible title, so the items are in the title bar row and the display-mode menu stays. The window sets `sceneBridgingOptions = []` on its hosting controller before the window takes it, so SwiftUI never replaces the toolbar or the title, and the title bar keeps its subtitle field (P5). No SwiftUI `.toolbar` is used. `allowsUserCustomization` and `autosavesConfiguration` are true, and `ToolbarCommands()` adds View > Show/Hide Toolbar (Option-Command-T) and Customize Toolbar…. The default set, leading to trailing: Add Track, space, Monitor Inputs, Go to Start, Stop, Play, Record, the time display, space, Split, Delete, flexible space, Zoom Out, Zoom In, Zoom to Session, Snap, Export, Inspector. The spaces make the groups (the macOS 26 glass groups). Cut, Copy, Paste, and Go to End are in the customization palette only. Priorities: Stop, Play, Record, the time display, and Inspector high; Monitor Inputs and Export over standard; Add Track standard; Split, Delete, zoom, and Snap low. Each item has a unique SF Symbol of macOS 14 or older; Record is `circle.fill` with a red symbol tint, and there is no `.prominent` style. Record, Monitor Inputs, Play, Snap, and Inspector are push-on-push-off buttons, so their on state is a shape, not only a color. The toggle items (`ToolbarItemID.allCases.filter(\.isToggle)`) have one width: the widest fitting width of the set. Such a button changes its own state at the click, before its action. So the click handler first sets the button state from the window state, and each state update compares the button with its control state: a refused Record, a Record click during a take, and a Play click at the session end show the true state. Each item has a short localized label, the menu text as its palette label, and a tooltip with its key (0010).

**Frozen identifiers.** The toolbar identifier is `dirigible.session`. The item identifiers are `track.add`, `record.monitor`, `transport.stop`, `transport.play`, `transport.record`, `transport.time`, `transport.start`, `transport.end`, `edit.split`, `edit.cut`, `edit.copy`, `edit.paste`, `edit.delete`, `view.zoom.out`, `view.zoom.in`, `view.zoom.session`, `file.export`, `view.inspector`, and `view.snap`. AppKit writes them to user defaults with the customization, so a rename loses the user layout. Never rename or reuse one; a new item gets a new identifier. A test holds the literal list.

**Chrome beside the window.** One object per window owns the toolbar delegate, the subtitle, the time display, the banner list, and the idle record-time read. It belongs to the window, not to the content controller. It derives one `Equatable` value from the window model in one observation loop and writes only the fields that change. Toolbar validation does not set the item states (`autovalidates` is false), because validation runs only after events. `SessionWindow` stays the model. Each toolbar item maps to one command (a timeline command, a transport command, or a window action: Add Track, Record, Stop, Monitor Inputs). Its palette label, its key, and its action come from that command. The toolbar calls one `SessionWindow` function, which forwards each command to the same place that its menu item reaches: the timeline command handler, `Studio.perform` for a transport command, or the window action, whose menu item also goes through that function. Cut, Copy, Paste, and Delete send the menu selectors to the first responder, so a focused text field takes them first (0018 E3). The one derived value also owns the record-over state; the display tick does not write it.

**No SwiftUI body reads `Studio.play`.** The time display is an AppKit view with a fixed size. It shows `h:mm:ss.t` during play (at most 10 text changes a second) or a take, and `h:mm:ss.mmm` when stopped. During a take, it shows the record head, the red line of the lanes. A chrome tick of 100 ms updates it, because no observed value carries the record head. The 100 ms limit of play does not apply to the tick: the tenths change at most about 11 times a second. The banners and the Stop menu item that need the playback state read stored values (the banner list, the record-over warning, `isRunning`) that the chrome loop writes only on a change.

**Window size.** A new window opens at min(1180 pt, the visible screen width) x 720 pt and cascades; the minimum content width is 720 pt, plus the inspector width while the inspector shows, so the transport and the time display never go to the overflow menu (P1c). An empty session shows one line of steps and one stack of actions: the prominent Add Track button above the Add Call Tracks menu, both of one width. The stack is centered in the area beside the inspector. Add Track is not a default button.

**Subtitle and banners.** The subtitle shows the rate, "Tracks: N" (no plural form, 0010), and the record time left under 3 h, from a Foundation units formatter, rounded down to the minute. The part follows the low-record-time rule before a take, also during a take, with its own shown state. The transport bar row goes. Its playback stop and missing media become banner rows; the record-over warning becomes a chip over the track headers, so the lanes do not move and no ruler time is under it. The chip shows "Hidden Audio at Risk" with the warning symbol in systemOrange. It is one menu button: a disabled line with the detail text (the track names and the start of the earliest clip; the consent sheet has its own text for the take start), Go to End, Show Clip, and Turn Off Record on each track of the warning. It has no close control. It reads one warning value that the chrome loop writes only on a change, and VoiceOver announces the warning once for each set of tracks: a show again of the same set stays silent. A low-record-time banner shows before a take under 3 h and hides 300 s over the limit, and during a take shows under 10 min and hides 60 s over the limit. Its text rounds the time up to the next whole minute ("Less than 2 hr, 1 min ..."). The window reads `Studio.remainingRecordTime(armed:)` at open, at an arm change, at focus, after a take, and every 10 s while idle. One read runs at a time: a trigger during a read asks for one more read after it, because a blocked `fstatfs` on a hung volume keeps its pool thread. The read only returns a value, and one function writes it only when the armed set did not change; during a take it reads `Studio.recordTimeLeft`, which the take start writes from the free bytes of its disk check and each disk check updates. The subtitle can be cut off in a narrow window; the banner is not. Each banner has a symbol by kind, a text that says what to do, an opaque 12 % tint, a 1 pt separator, and no shadow, material, or animation. The banner buttons and the import progress bar sit inside the tint, in a trailing actions slot. The slot is outside the ignored accessibility element of the symbol and the text, so VoiceOver reaches each button. A new banner is announced to VoiceOver (high for a playback stop and the low record time).

**Keys.** Each toolbar item is a menu item with a key (F16). Monitor Inputs gets Shift-Command-M. Stop moves to the Transport menu. Stop (Command-period) stops a take; with no take, it stops the play and keeps the playhead, as the Stop item does. Stop never discards a take: the take finalizes and stays in the session. The Stop item and menu item are on only when a take or a play runs, so Command-period still cancels a sheet when nothing runs.

**Track header panel (run 1b).** The headers stay in the vertical ruler of the lanes scroll view (0017), not in a split pane. A handle at the trailing edge of the ruler (a 6 pt hit area inside the header padding) sets the width: 180 to 480 pt, default 340 pt, an app preference in user defaults that each new window reads once, at its open. A pane that SwiftUI builds again (all tracks deleted, then Undo) keeps the width of its window. A double-click sets the default. Esc during a drag restores the start width. The width type clamps, so an out-of-range width cannot exist. It rounds to whole points, so the header edge is on a pixel edge at scale 1 and 2. The preference key is `timeline.header.width`, a `Double` of points; it never changes its meaning or its type (0024 P11). A header drag does not hold the lanes width; the lanes take the new width at each event. The width and the drag state machine are pure values in `DirigibleTimeline`. The ruler draws an opaque background, so no lane content shows through the headers. The lanes get a dark palette in Dark Mode, so an opaque dark header never sits next to light lanes. A drag applies the width at each event. If that misses the budget, the fallbacks go in order, each measured again: the surface capacity from the clip view width when the lanes part of the event is over 8 ms p95; then a fixed header host width during the drag, applied at the mouse-up, when the event is still over the budget; then a guide line.

**Surface capacity (0022).** If the lanes part of a header drag event (the same event with no header rows) is over 8 ms p95 with the 0022 capacity (from the shown width), the capacity of a lane surface keys on the clip view width, so a drag keeps the 4 slots and renders only the new columns. The run records which fallbacks hold, with the bench numbers. Outcome (run 1b slice 1, `make bench FILTER=HeaderDragBenchmark`, the Intel Mac of the probes): with the 0022 capacity, one event took 27.5 ms p95 at fit zoom and 29.5 ms with 60 pt boxes, and 19.0 ms and 20.9 ms with no header rows. With the capacity from the clip view width, two runs gave 14.9 and 13.0 ms at fit zoom and 14.5 and 15.3 ms with 60 pt boxes, and 6.1 to 6.9 ms with no rows. So the first fallback held in slice 1, with the header rows at about 8 ms of the event. In slice 5 the name field and the route menu flex with the width, and the rows with a flex layout took 17.1 to 19.5 ms p95 (15.2 and 18.8 ms with a single row stack). So the second fallback landed: the rows keep their width during a drag, the ruler clips them, and they take the width at the mouse-up, Esc, a double-click, and an AX step. Two runs then gave 6.7 to 8.9 ms p95 with rows and 6.1 to 7.5 ms with no rows. The guide line is not used. The one-off events lay out the rows at the new width and have no p95: after code gate 1 (the row layout from the width only, and a compact route and state on a one-line row), two runs gave a drag p95 of 6.5 to 8.8 ms with rows and these one-off times with rows: Esc 6.0 to 6.8 ms, a mouse-up at 400 pt 5.8 to 7.6 ms, a double-click 8.9 to 11.2 ms, an AX step 9.7 to 11.2 ms, and a mouse-up at 183 pt (the rows drop the layout text) 17.9 to 22.5 ms, one frame late once per drag. After code gate 2 the bench gates a one-off event at two frames (32 ms) and adds one-line rows (50 pt lanes, a take on each track, a lost device): two runs gave a drag p95 of 6.8 to 8.3 ms with rows and 5.6 to 6.6 ms with one-line rows; the one-off events took 4.5 to 11.8 ms, and the mouse-up at 183 pt 14.7 to 20.0 ms.

**Content controller.** The content stays one `NSHostingController` of `SessionView` (0014). The inspector is a SwiftUI column of `SessionView`, not an `NSSplitViewController` (amended 2026-10-04). The chrome does not move, because it belongs to the window. `fullSizeContentView` stays off, so no lane pixel is under the toolbar material.

**Inspector width (amended 2026-10-11).** The inspector is 240 to 400 pt wide, default 270 pt. The width is the app preference `view.inspector.width`, a `Double` of points, that each new window reads. The width rounds to whole points. A missing value, a text, or NaN gives 270 pt. An out-of-range value clamps to 240 or 400 pt. The width also clamps to the content width minus 720 pt, before the model takes it, so a drag never widens the window. A 6 pt AppKit handle view over the 1 pt divider sets the width. The handle reads `event.locationInWindow.x`, because the column origin moves with the width. A double-click sets 270 pt and saves it. Esc during a drag gives the start width and saves nothing. During a drag the pane and the lanes keep their width, and a 1 pt accent line over the window content shows the target edge. The mouse-up sets the width and saves a changed width. A live width missed the 16 ms budget at 2 h (p95 26 ms; C16, 2026-10-11), so the inspector takes the guide-line fallback; a drag event then runs no SwiftUI body and draws no lanes (p95 under 1 ms), and the mouse-up takes about 26 ms, once per drag. The handle is an accessibility splitter with the label "Inspector width" and steps of 20 pt. The inspector handle and the track header handle share `PaneDrag<Width>` over the `PaneWidth` protocol in `DirigibleTimeline`.

**Budgets.** A play tick (run 1a) and a header drag event (run 1b) each take 16 ms p95 or less at 2880 x 1200 px, optimized, one event per 60 Hz frame (`make bench FILTER=HeaderDragBenchmark`, `FILTER=PlayTickBenchmark`). No earlier bench case gets worse than main by more than 10 % or 1 ms (0022).

**CLI (0011).** No command. The toolbar, the subtitle, the banners, the header width, and the inspector width are app chrome. The record time left uses the existing `Studio.remainingRecordTime(armed:)`.

## Consequences

- 0014 gets an amended line: the AppKit toolbar, `ToolbarCommands`, the subtitle, `sceneBridgingOptions = []`, the chrome object beside the window, the window size (1180 x 720 pt, minimum width 720 pt), the empty state, and Command-period for a take or a play in the Transport menu.
- 0015 gets an amended line: Monitor Inputs is a toolbar toggle and a menu item with Shift-Command-M; the window check box goes.
- 0016 gets an amended line: the transport bar goes; its controls are toolbar items and its warnings are banners.
- 0017 gets an amended line: no SwiftUI body reads `Studio.play`, and record-over is an overlay (run 1a); the header width is 180 to 480 pt with a drag handle, the header ruler is opaque, and the lanes have a dark palette (run 1b).
- 0022 gets an amended line only if the capacity rule lands.
- The chrome loop runs at each playhead poll during play, and every 100 ms during a take. It builds and compares one small value; the play tick bench case measures it.
- The customization layout lives in user defaults under the toolbar identifier, for all windows.
- The header width of one window does not change the other open windows until their next open.

## Alternatives considered

- **A SwiftUI `.toolbar(id:)` through the scene bridge.** Rejected: UUID identifiers (U3), no visibility priority, possible labels, or centered items, and the time display would be a SwiftUI view that updates at the poll rate.
- **`SessionWindow` as the toolbar delegate.** Rejected: about 250 lines of item code in the window model, which is at 389 of 400 lines.
- **An `NSSplitViewController` now.** Rejected: a split view for one item. It comes with the first side pane.
- **A split pane for the track headers.** Rejected: two scroll views need a vertical scroll sync, which 0017 avoids.
- **The time display set by the display link of the lanes.** Rejected: a session with no tracks has no lanes view, and it would be a second writer of the chrome.
- **A guide line during the header drag, applied at the mouse-up.** Kept as the last fallback only: it gives no live feedback.
- **The `.prominent` Record style of macOS 26.** Rejected: HIG gives it to one primary action on the trailing side; the red symbol tint gives the same signal on every system.
- **A Stop menu item that is always on.** Rejected: it takes Command-period from the export sheet when nothing runs.
