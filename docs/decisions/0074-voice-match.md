# 0074. Voice match: a live EQ stage of the track, after the rendered levels

- Status: accepted
- Date: 2026-11-16
- Accepted: 2026-11-16, after the plan gates (2 rounds) of the re-plan of run `2026-10-14-voice-match`.
- Amends: 0003 (the `<match>` element of a track), 0024 (the version table: version 18 with a voice match), 0054 and 0057 (a voice match is not a clip render and writes no origin element; 0057 D9 "Each later kind (hum, ride, match) adds its element" no longer holds for match), 0064 D2 (the chain order holds for the rendered kinds; the match stage runs live after the top rendered level, see D7), 0016 (the mix of the Player runs a filter stage), 0002 (no change of the targets; new files in `DSP/` and `Render/`).

## Context

A tester asked for the Voice Profiler of Hindenburg in the track header. F37 says "learned EQ per voice". An earlier plan rendered the match EQ into a new WAV for each clip, as a level of the 0057 origin chain. A live stage is a better option. Each render writes about 518 MB for 1 h of mono (0054), and each change of the amount renders again. The only stated reason against a live effect is the 56 to 76 ms latency of the noise unit (0057, Alternatives), and an EQ has no such unit.

Facts of the code on main c46b2ca1f:

- `MixReader.render(_:into:)` (`Sources/DirigibleAudio/Render/MixReader.swift:55`) is the one mix of the Player (`Player.swift:180`), the export (`Export.swift:106`), and the mix scans (`DSP/MixLevels.swift:16`, `:50`). For each heard track and each sounding clip part, it reads the file frames and adds them with one gain vector: clip gain, track gain, fades, envelope, and ride (`MixReader.swift:60-117`). It keeps no state from one range to the next, except open files and scratch buffers.
- The Player calls it on the serial queue of the actor (`Player.swift:39`, QoS user-interactive), from a refill tick each half chunk (`Player.swift:189`; chunk 0.1 s, `:126`), and keeps 3 chunks scheduled ahead of the node (`Player.swift:26`). The Core Audio render thread only plays scheduled buffers. So no code of the mix runs on a real-time thread.
- A play renders overlapping ranges: the vari-speed read takes `span + 2` frames (`Player.swift:291`), and a crossfade renders a chunk again with the old session (`Player.swift:312-333`). The export renders chunks of 48,000 frames (`Export.swift:45`).
- The Level Over Time layer (0060) is the model: a read job measures (`Studio+Ride.swift:21`, `runReadJob` in `Studio+Level.swift:31`), the session stores the result (`Clip.ride`), and `MixReader` applies it at each read.
- The render levels of 0057 are in the file: a clip on a rendered file reads the top level of its chain. The stage reads the same file, so it runs after every rendered level (noise, hum, rumble, de-clip, de-ess).

Reference behavior (`docs/research/voice-match.md`): Hindenburg applies the Voice Profiler live as a track plugin with a bypass. A Hindenburg PRO session of a tester stores it as `<Plugin Name="Voice Profiler" UID="nhft">` in the `<Plugins>` of a `<Track>`, with a high-pass, a low band, a mid band, and a high band (gain, frequency, Q, type each), a `Comp` value, and `Bypass="False"`, before the Noise Reduction plugin of the same track. Logic Match EQ and Ozone Match EQ are live plug-ins with an amount; Ozone uses a linear-phase EQ with "over 8,000 bands".

## Rubric

1. The same samples for play, export, and each mix scan, for any read size and order.
2. No latency that a listener hears, and no filter state in the random-access mix.
3. The refill cost on an Intel Mac stays inside a measured budget.
4. One small stored value, one version raise, and a seam that a later de-ess stage can use.
5. At least the reference behavior: live, per track, bypass, amount, and a finer curve than four bands.

## Decision

**D1. Place.** One match stage for each matched track, in `MixReader`, on the track bus. For a heard track with a match, the clip loop of `MixReader` renders the track over the render range plus the context of D2 on each side into a stereo track scratch: the file frames of each sounding clip times its gain vector (clip gain, fades, envelope, ride, and track gain). The stage filters the scratch once and adds its center frames to the mix. So the stage hears the track as it plays, after the clip gain and the fades, the order of a Hindenburg track effect. A timeline frame outside every clip is zero, and a file frame outside a clip is never read: audio that the user cut away is never heard, and a split plays as the unsplit clip. The track gain is one constant factor, so its place before the stage changes the output only by rounding. A track with no match, or a bypassed match, keeps the plain loop.

**D2. Filter form.** A linear-phase FIR, made from the curve by frequency sampling and a window, and applied by FFT overlap-save with `vDSP`.

- Kernel: 16,385 taps at 48 kHz, a Kaiser window with beta 5, and a design grid of 32,768 points. A probe at the plan gate measured that 8,193 taps misses the response bound at 80 Hz with the Blackman, Kaiser, and Hann windows (2.26 to 3.07 dB), and that 16,385 taps with Kaiser beta 5 meets it (1.10 dB at 80 Hz).
- Rate rule: the session rate is any positive integer (`Session.swift:19-21`; the app makes 48 kHz sessions, and `dirigible new --sample-rate` takes any rate). Taps: the power of two at or over rate x 16,384 / 48,000, plus 1, so the kernel spans 341 ms or more and keeps the frequency resolution of 48 kHz. The design grid and the block are 2 x (taps - 1) points. So 16,385 taps and blocks of 32,768 points at 32, 44.1, and 48 kHz; 32,769 and 65,536 at 88.2 and 96 kHz; 65,537 and 131,072 at 176.4 and 192 kHz. The response bound holds at 44.1, 48, and 96 kHz with this rule, and 16,385 taps at 96 kHz misses it (2.26 dB at 80 Hz).
- Out of band: a boost at an end band goes to 0 dB at the band edge, dB linear on log f, from 63 Hz to 56.1 Hz and from 16 kHz to 17.96 kHz. A cut at the 63 Hz band holds to 56.1 Hz and goes to 0 dB at 28.1 Hz; a cut at the 16 kHz band follows the boost rule. Each bin past these points is 0 dB, the DC bin is 0 dB (gain 1), and each bin at and over 0.45 x the session rate is 0 dB. So no boost lies outside the band range.
- Context: the stage renders (taps - 1) / 2 timeline frames (8,192 at 48 kHz) before and after the render range. Before session frame 0 the context is zeros. So the filter is non-causal and has no delay.
- Block plan: blocks of 2 x (taps - 1) points with taps - 1 output frames each (32,768 and 16,384 at 48 kHz). A render of n frames takes ceil(n / (taps - 1)) blocks for each channel: at 48 kHz 1 at 1x play (4,801 frames), 2 at 4x (19,202 frames), and 3 for each export or scan chunk (48,000 frames); at 96 kHz 1, 2, 2 for each export chunk (48,000 frames), and 3 for each scan chunk (1 s, 96,000 frames, `MixLevels.swift:121`).
- Gate: the filtered center frames are multiplied by the clip extents of the track before they go into the mix. Clips that touch or overlap make one extent. Inside an extent the gate is 1. Outside each edge of an extent, a raised-cosine ramp goes from 1 at the edge to 0 at the ramp length R from it, and past R the gate is 0. R is 16 ms at a hard edge (one period of 63 Hz, under the about 20 ms of pre-masking; 768 frames at 48 kHz, scaled with the rate), and the longer of 16 ms and the clip fade at an edge with a fade, and at most (taps - 1) / 2 frames (8,192 at 48 kHz), where the ring of a clip ends. Reason for the cap: the render reads the clips over the range plus that context, so a longer ramp would put the gate of a frame on a clip that a short render does not read, and the output would depend on the render range. Where the ramps of two extents overlap (a gap shorter than the two ramps), the gate is the larger value. So the gap past R is bit equal with the unmatched track, and the ring inside R is faded. A split or a crossfade join adds no edge, so the gate of the split session equals the gate of the unsplit session. The render builds the gate from the clips that it already reads, into a scratch of the reader: no allocation and no lock. The kernel stays linear phase; the ring inside a clip, before a transient, is for a listen check (Reverse: a minimum-phase kernel).
- No state: each output frame is a function of the session only. So rubric 1 holds by construction, and a test asserts it.
- Kernel cache: at most two kernel spectra for each track, the current and the previous session, keyed by the 25 values of `VoiceMatch.gains(at:)`, which hold the curve and the amount. A new key replaces the older entry. So a crossfade chunk after one update renders the old session with no new design, and an Amount drag designs one kernel for each drag step (1.28 ms p95 at 48 kHz on an Intel Core i5-8259U).
- Design off the render: the `MixReader` init and its `session` setter design each kernel that the cache does not hold, and size the track scratch for the largest render span of the reader (an init value: the 4x span of the Player, the chunk of the export and of the mix scans). `render(_:into:)` only reads the cache and the scratch: it designs nothing, takes no lock, and allocates nothing. A render longer than that span runs in pieces of the span; each output frame is a function of the session only, so the pieces give the same output.
- Threads: one queue owns each reader, so the cache needs no lock. The Player makes its reader in `apply` before the first refill (`Player.swift:178-181`) and sets the session in `update` (`:202`), both on the Player queue (`:39`), where each refill also runs. The export and each mix scan make and read their own reader on their own thread. The crossfade sets the old session for one render (`Player.swift:316-318`). After one update in a tick, its kernels are in the cache, so that set designs nothing. After two or more updates in one tick (Amount drag steps), `update` keeps the first old session as `fadeFrom` (`Player.swift:198-200`), the cache holds only the last two, and that set designs the missing kernel on the Player queue, off the render. No real-time thread runs the stage: the Core Audio render thread plays only scheduled buffers, so 0013 **Callbacks** covers no code of the stage. Cost: a play start of 8 matched tracks designs 8 kernels before its first refill, and a Match of 8 tracks designs 8 kernels in `update` before the next tick. At 96 kHz a design takes 4.23 ms p95, so a cold start of 8 tracks takes about 52 ms at 1x and 69 ms at 4x (an estimate, not measured).

**D3. Stored value.** `Track.match: VoiceMatch?` in `DirigibleCore`, a value with no audio read and no framework:

- `amount`: a `VoiceMatch.Amount`, whole percent from 1 to 100. A new match takes `VoiceMatch.defaultAmount`, 75.
- `isBypassed`: a bypassed match keeps every value, and the mix plays the track with no match stage.
- `reference`: the name of the reference clip at the match (`Session.name(of:)`: the path of its file with no ".wav"). It does not follow a later edit or delete of that clip.
- `curve`: the curve at 100 %, 25 gains in dB (`ThirdOctave.Gains`), one for each one-third-octave band from 63 Hz to 16 kHz, after the cap and the guards: -12 to +12 dB.
- `targetPowers`: the gated band powers of the target track (25 finite values of 0 or more), the weights of the loudness offset.

Only the checked init makes a value, so each stored value is in range. `VoiceMatch.gains(at:)` gives the band gains at an amount: the curve times the amount, minus one offset in dB that keeps the K-weighted power of the target bands. The K weight of a band is the power gain of the BS.1770 filter at the band center, with the coefficients that the standard gives for 48 kHz. The offset divides the powers by the largest one first, so no sum overflows, and a target of zeros gets 0 dB. The offset keeps on and off at one loudness, not one peak, so the largest stage gain can be over the 12 dB cap. `VoiceMatch.extremes(at:)` gives the largest boost and cut of the curve times the amount, with no offset, to 0.1 dB, and +0.0 when the curve has none. The filter makes each band at or over 0.45 x the session rate 0 dB (D2), so `gains(at:)` leaves those bands as they are.

**D4. Format.** `<match amount="75" reference="<name>" curve="g1 ... g25" target="p1 ... p25"/>` in `<track>`, after `<route>`, each list number in `Double.description` with one space between numbers, and `bypassed="true"` only on a bypassed match. The bypass and the name are attributes of the one element, so they raise no second version. `session.xml` is version 18 (`matchSessionVersion`) when a track has a match (0024 P7). A track with no match writes no element, so a session with no match keeps its lower version (P6), also after the remove of its last match. The reader refuses a `<match>` in a file of version 17 or lower, more than one `<match>` in a track, a missing `amount`, `reference`, `curve`, or `target`, an amount that is not a whole number from 1 to 100, a list with a count other than 25 or an empty item, a gain outside -12 to +12 dB, a power that is negative or not finite, a `bypassed` other than `true` or `false`, and a reference with a control character. Split Stereo to Mono gives each mono track the match of its stereo source.

**D5. Measure.** A read job, `Studio.matchVoice(reference:tracks:amount:)`, on a new transport case `.matching`, as `levelOverTime`. It reads the reference clip and the clips of each target track in one way: file and clip gain, with no match stage; the reference clip is left out of its target track. Reason: one read path, and a reference on a matched track is rare. Reverse: read the reference through the match of its own track. It averages Hann frames of 8,192 with a hop of 4,096 that lie inside BS.1770 blocks that pass both gates (`LoudnessMeter` steps), into the 25 band powers. Less than 10 s of gated voice refuses `tooLittleVoice`. The apply step sets `Track.match` of each target track as one undo entry. A change of the amount only, and a removal, read no audio.

**D6. Player.** A change of the match of a heard track crossfades the next chunk, as a track gain change does (`Player+Feed.swift:28`).

**D7. Chain order.** The rendered kinds keep the order of 0064 D2 inside the file. The match stage runs after the top level. So a clip with a rendered de-ess level hears de-ess before the match, not after it as 0064 D2 says. A later run can move de-ess onto a live stage after the match. Until then the guide says it.

**D8. Front ends.** `dirigible track match-voice <package> --reference <clip> <track>... [--amount <percent>]`, `dirigible track match-voice <package> --amount <percent> <track>...` (a track with a match), and `dirigible track match-voice <package> --remove <track>...`; the tool `track_match_voice` (0041, a batch step of 0063); `info` shows the amount and the largest boost and cut. The app control is a mark after the track name that opens a popover with the reference name, the Amount slider, Bypass, and Remove.

## Consequences

- No new WAV for a match, and an amount change costs no audio read and no disk.
- New clips on a matched track (a new take, a paste, an import) play matched, as with a Hindenburg track plugin.
- Each play, export, and mix scan of a matched track runs the stage: 2 FFTs of 32,768 points for each channel and each 16,384 output frames. Measured on an Intel Core i5-8259U: 3.14 to 3.41 ms p95 for a 1x chunk of 8 matched stereo tracks, and 6.22 to 6.34 s added to each mix pass over 60 min of 2 stereo tracks. An export with a loudness target runs 2 to 6 mix passes (WAV at the session rate, the app default) or up to 16 (MP3, AAC), so it pays the stage cost once for each pass. The mix scans read chunks of 48,000 frames, so they pay the export cost for each frame. At 96 kHz each cost is about 2.5 times as large.
- The waveform peaks come from the file, so the lane shows the audio before the match. The track bus does not change this.
- The learn reads file and clip gain for the reference and the targets (D5), and the loudness offset of D3 does not depend on the place of the stage.
- A crossfade on a match change renders the old session from the kernel cache. An export of a track set runs the stage of each matched track in the set; no export reads tracks apart (`ExportParts.swift` splits by time). Clips that overlap on a track (a crossfade) are summed after their fades, then filtered once.
- A hard clip edge (no fade) is filtered as heard, so the kernel rings before and after the edge. With no gate the ring goes into the silent gap: a probe measured -34.5 to -50.3 dB against the clip peak more than 20 ms before the edge in the worst voice cut. The gate of D2 keeps the gap silent.
- Match Voice can raise peaks: the offset keeps the K-weighted power, not the peak. On a corpus pair the true peak rose 3.7 dB at amount 75 and 4.6 dB at 100, under the largest stage gain; a lower boost cap does not lower the rise. No peak guard: equal loudness of on and off wins, as for the track fader and Logic Match EQ, so a full match can raise the true peak by about 4.6 dB and clip in play. The popover shows the largest boost, and the guide says to lower the track or to export with a loudness target. The play path shows an over only on the mix: the loudness strip (0033) shows the true peak of the heard mix and turns Peak red over -1 dBTP, only in a 1x forward play. No track shows a clip, and the Player has no limiter. Reverse: a peak term in the offset, at the cost of 1.6 LU on that pair. An export with no loudness target has no limiter (`ExportTypes.swift:8`). The guide says it.
- Auto Level and the ride measure read the file and the clip gain, not the mix, so they do not hear the match. The loudness offset of D3 keeps the K-weighted level of the target spectrum, so the error is the program difference.
- A paste into another package copies the clips, not the track value, so the copy plays unmatched.
- A linear-phase FIR rings before a transient for a curve with steep changes.

## Alternatives considered

- **Render into a new WAV.** Rejected: a WAV for each change, about 518 MB for each hour of mono, a render for each amount change, and an origin level that 0057 D4 must rebuild. Hindenburg, Logic, and Ozone keep the match live.
- **A stage on each clip part, read from file frames.** It filtered the file frames of each part, with 4,096 file frames of context on each side, before the gain vector. Rejected: it made up to 85 ms of cut-away audio audible at each cut, it needed tests for edge cases that a track stage does not have, and it cost twice the blocks (4.31 ms against 2.05 ms p95 at 1x). It is the Reverse of D1.
- **A track bus stage with a biquad bank (`vDSP.Biquad` or `AVAudioUnitEQ`).** The mix sums the clips of a track, then runs a parametric bank with state. It needs state across reads, a reset and a warm-up read at each seek, and the export and the Player then differ at each seek and each crossfade chunk. 25 bands interact and need a fit (Liski and Valimaki 2017). Rejected on rubric 1 and 2.
- **A curve on each clip (as the ride).** A split and a paste keep it, but a new take on the track plays unmatched, and the tester asks for the track header. Rejected on rubric 5; a clip override stays a later item.
- **A minimum-phase FIR (cepstrum fold).** The same cost and no pre-ring, but the phase changes with the curve. Kept as the Reverse of D2 if a listen check hears pre-echo.
- **Store the reference spectrum, not the curve.** A re-match with no reference clip needs it, but the guards also need the target noise, and no front end reads it. A profile library (Hindenburg Profiles folder) is a later item.
