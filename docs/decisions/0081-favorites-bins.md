# 0081. Clip bins in session.xml, and Favorites as one Dirigible package in Application Support

- Status: accepted
- Date: 2026-11-23
- Amends: 0002 (the locked read-edit-save step is in `DirigibleAudio`), 0003 (`<bins>` from version 21), 0024 (a bin clip holds a `Clips/` WAV), 0060 (a bin clip finds its ride list by value), 0042 (one file copier with two callers; a lane with no target track gets a new last track), 0018 and 0038 (Paste and Insert add tracks for lanes past the last track), 0023 (the Bins segment of the leading pane), 0011 (`dirigible bin` and `dirigible favorites`).

## Context

F22 asks for named groups of clips in a session (bins). F23 asks for Favorites: one clipboard that all sessions share. Hindenburg keeps the clipboard groups in the session file, and the Favorites in `~/Library/Application Support/Hindenburg` as `Favorites.xml` and a `Favorites` audio folder ([research](../research/favorites-bins.md), sections 4 and 5). Descript keeps project media after the user removes a library item (section 6).

Constraints from this repo:

- 0024, amendment 2026-10-12: "Only a clip holds a top-level `Clips/` WAV: a clip of `session.xml`, or of a readable backup, or of the app clipboard. A pool entry with no clip does not hold it. ... A new holder raises the `session.xml` version or keeps its audio out of `Clips/`." A bin clip is a new holder.
- 0042: `pasteClipboard` is "the one function that copies files". A paste from another package copies each file under a new file ID; Undo keeps the copies.
- `Session.filesInUse` (`Session+Origin.swift`) is the one rule of Remove Unused Files (`UnusedFiles.usedPaths`). `Session.removeFile` had its own copy of the rule.
- `Session.paste` gives each pasted clip a new ID (`derivedID`), so a stored excerpt can keep the IDs of its source clips.

## Decision

- **Bin.** `Session.bins: [Bin]`, in user order. A `Bin` has a `BinID`, a name, and `items: [BinItem]`. A `BinItem` has a `BinItemID`, a name, and only what the file holds: the excerpt kind, the length, and the lanes with their clips, at the session rate. It holds no file record and no transcript words, so a session equals the value that `session.xml` reads back (`checkedData`). A name is trimmed and not empty; two bins or two items can have the same name. Each edit is one `Session` edit, so it is one undo entry: add, rename, move, and remove a bin; add, rename, and remove an item. Items have no move.
- **Holder.** A clip of a bin item is a holder, as a clip of a track. One internal set, `clipFiles`, holds the files of track clips and bin clips: `removeFile` checks it and keeps its `.fileIsSource` refusal for the source of a used rendered file, and `filesInUse` adds the origin closure to it. The pool record of `session.xml` is the one record of each file. `addItem` refuses an excerpt at another rate, a clip whose file record differs from the pool record (`.foreignFile`), and a used `BinItemID` (`.duplicateID`).
- **File.** `session.xml` at version 21 (`binSessionVersion`) has `<bins>` after `<exportPresets>` and before `<recording>`: `<bin id name>`, `<item id name kind length>`, `<lane source name layout>`, and the `<clip>` element of a track clip, with the same reader and writer. A bin clip names its ride list of `<rides>` (0060) by the value of its ride, not by its clip ID, because it keeps the ID of its source clip and two items can hold one ID. The reader checks each bin clip as a track clip (file, extent, layout, lane order). A session with no bin writes no element and keeps its version. A file below version 21 with `<bins>` is refused.
- **Templates.** `newEpisode()` (0079) keeps the bins and, through `filesInUse`, the WAVs of their clips.
- **Paste from a bin.** `Session.excerpt(of: item)` builds the `Excerpt` from the current pool, and it becomes a `Clipboard` of its package and goes through `pasteInPlace` (same package) or `pasteAcross` (another package). A lane with no target track gets a new last track named after the lane, with the lane layout: for `.unselected` when its source track is gone, and for `PasteTarget.extending(ids)` of the window Paste and Insert when the tracks under the first selected track are too few. `.tracks(ids)` stays an exact list, so Replace, Paste to Fill Selection, and the CLI `--onto` still refuse a wrong count.
- **Favorites store.** One Dirigible package, `Favorites.dirigible`, in `~/Library/Application Support/com.delineas.dirigible/`, at 48000 Hz. `DIRIGIBLE_FAVORITES` sets another path. Its bins are the favorite groups; the first add to an empty store makes the bin "Favorites". An add makes the store folder and each missing parent folder (`createDirectory` with intermediate folders, which accepts a folder that exists); it never calls `Session.create`, which writes `session.xml` with no lock. The app never opens the store as a session window by itself.
- **One file copier.** `copyExcerptFiles` (`DirigibleAudio/Import/ExcerptCopy.swift`) holds the file half of a paste across packages: the new records, the stems, the clone, copy, or conversion, the read-back, and the map of the excerpt to the new records. It runs a `place` closure on the target session with the predicted lengths before the first copy, and with the real lengths before the renames. The track paste (`pasteClipboard`, whose `place` is the target tracks and `Session.paste`) and the favorite add (whose `place` is `addItem`) are its two callers. A record with a span copies only those frames of its source file, through the conversion of import at the same rate or at another rate; a record with no span copies its whole file. Only the favorite add gives spans: the track paste copies whole files (0042). `PasteTarget` names tracks only.
- **Store edits.** `editPackageCore` (`DirigibleAudio/Import/PackageEditCore.swift`) is the one package edit step: the lock, a fresh read of `session.xml`, the edit, the write. Each store write runs through it: `Favorites.add`, and `Favorites.edit` for each rename, remove, and new group, by `BinID` or `BinItemID`, so an edit from an old list cannot drop an item that another writer added. For the add, a store folder with no `session.xml` (ENOENT at the read: a crash during the first write, or a racing first add) is an empty 48000 Hz session that the step writes under the lock (`whenMissing`); every other package keeps its read error.
- **Add to Favorites.** `Favorites.add` makes one `BinItemID`, runs `copyExcerptFiles` from the source package into the store with `addItem` of that ID as its `place` step, inside `editPackageCore` of the store, and returns the ID. The ID is made before the two runs of `place`, so the returned ID is the stored one. So the add gets the stem rule, the clone or copy, the conversion at another rate, the space check on the store volume, the cancel, and the renames of 0042. The store gets its own copies, so a later edit or prune of the source changes no favorite.
- **Only the played frames.** A favorite stores only the frames that its clips play (`Excerpt.cropped`), so a 5 s sting from a 1 h recording stores about 5 s of audio. A clip plays its file range and half of each of its crossfades. The extents of one file that touch or overlap form one run, and each run that is not the whole file becomes one store WAV; the clip offset, envelope, and ride move by the run start (`GainEnvelope.moved`, as a render repoint). At another rate, each run grows by 2048 frames at each edge, capped at the file, and starts on a multiple of the frames in which the two rates meet (147 at 44100 Hz), so the converted run has the samples of a conversion of the whole file. A paste of the favorite renders the same samples as a paste of the source range. A clip set that plays a whole file clones or copies it.
- **Add in the app.** A favorite add is a blocking run of the source window (`ImportRun.Kind.favorite`). The work returns no made file and writes the store `session.xml` as its last step, because a blocking turn removes the made files of a work that leaves the studio session unchanged. A Cancel or a take start after the store write still reports a stop; the favorite stays in the store, and the window reads the store again after each result. One `@MainActor` model on the app delegate holds the loaded store list, reads the store and runs each store edit off the main actor, and reloads after each store write of the app, at each app activation, and at each show of the Bins segment, because the CLI or an MCP client can write the store. A reload returns only when the list holds the newest read. That model is the one writer of the store in the app: it runs each add and each store edit one after the other. A Cancel of an add that waits for an earlier store write ends the add at once, and the add writes nothing; an add whose turn comes after its Cancel writes nothing either, also with no file to copy.
- **Paste from Favorites.** A `Clipboard` with the item excerpt (built from the store pool), the store path, and the store identity, through `pasteAcross`. It copies each file into the target package under a new file ID. A session never names a file outside its package, so a session opens on another Mac with no favorites store.
- **CLI and MCP (0011).** `dirigible bin` and its `bin_*` tools work on any package path, also the store. `dirigible favorites path` prints the store path, and `dirigible favorites add` and `favorites_add` copy a range or clips of a package into a store bin. The source is read with no lock, as `info`. `favorites_add` is refused while a window has the source open, as a paste from another package. The CLI test children get a store path in their own folder, so no test writes the store of the user.

## Consequences

- An older app refuses a session with a bin ("unsupported version"), and does not change it (0024).
- The store grows: a removed favorite keeps its WAV until Remove Unused Files runs on the store (`dirigible file prune <store path>`), and then only when no backup names it. The store has no session undo, so each store write keeps a backup (`BackupPolicy.store`, chosen by `editPackageCore` for the package at `Favorites.package(environment:)`, so also for a write of `dirigible bin` or a `bin_*` tool) and the 3 newest stay, not the 20 of a session (0043). The WAV goes free after 3 later store writes. Another package edit keeps the standard policy.
- A paste from Favorites copies the audio again for each paste, as a paste from another package (0042).
- Two processes that write the store (the app and the CLI) take its lock for each write; the second gets a busy error and writes nothing.
- A bin item stores no transcript words. A paste from a bin in its own package changes no words (0055: only a paste from another package adds words). The store keeps no transcripts, so a paste from Favorites brings no words.
- A user who opens `Favorites.dirigible` in the app holds its lock; each add then fails with the busy error until that window closes.
- An add from a 44.1 kHz session converts each file to 48000 Hz. The store rate and path are one-way after the first release with Favorites.

## Alternatives considered

- **A folder of WAV files and an index file (as Hindenburg).** Rejected. It needs a new format with its own version (0024), a second writer of audio, and a paste through Import Audio (0040) that loses the clip edges, gains, fades, and the lanes of a range.
- **A path reference from a session to the store.** Rejected. The session breaks on another Mac and after a favorite removal; Hindenburg tells the user to move only the session and its `Files` folder.
- **One store package for each sample rate.** Rejected for now. It removes one conversion at a 44.1 kHz session, but adds a package choice to each add and each list.
- **A full `Excerpt` in each bin item.** Rejected. The excerpt carries transcript words, `pastesWords`, and copies of the pool records, which the file does not hold, so the session never equals its read-back and each save fails.
- **A bin case of `PasteTarget`.** Rejected. `at` and `insert` mean nothing for a bin, and the paste result cannot carry the new item ID.
- **Bin items as single file ranges (file, offset, length).** Rejected. A Hindenburg clip can hold several regions and region groups, and `Excerpt` already carries lanes, edges, gains, fades, and envelopes into `Session.paste`.
- **Bins in a sidecar file next to `session.xml`.** Rejected. Undo, the backups, and the atomic save cover `session.xml` only, and the holder rule would need a second reader.
