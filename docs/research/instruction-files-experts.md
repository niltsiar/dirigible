# Expert views: self-editing agent instructions and small instruction files

Date: 2026-09-30

Access date for all URLs: 2026-09-30. "WebFetch" quotes came through a fetch tool that summarizes pages. A text in quote marks is near-exact. Check the URL before you cite a quote in a decision record.

## Findings

1. **Karpathy names the idea: "system prompt learning".** "Pretraining is for knowledge. Finetuning (SL/RL) is for habitual behavior. Both of these involve a change in parameters but a lot of human learning feels more like a change in system prompt. You encounter a problem, figure something out, then 'remember' something in fairly explicit terms for the next time." Andrej Karpathy, X, May 2025. https://x.com/karpathy/status/1921368644069765486 (x.com returned HTTP 402; text read via api.fxtwitter.com mirror, secondary copy of a primary post).

2. **Karpathy: the edits are the open problem.** "It should come from System Prompt learning, which resembles RL in the setup, with the exception of the learning algorithm (edits vs gradient descent)... With a lot of details left to figure out (how do the edits work? can/should you learn the edit system? how do you gradually move knowledge from the explicit system text to habitual weights...?)". Same post. Note: he also says such knowledge "certainly shouldn't come from human engineers writing system prompts by hand", and he cites a roughly 17,000-word Claude system prompt as the trigger. This is a proposal, not a measured result.

3. **Karpathy: context engineering.** "In every industrial-strength LLM app, context engineering is the delicate art and science of filling the context window with just the right information for the next step"; "Too little or of the wrong form and the LLM doesn't have the right context... Doing this well is highly non-trivial." Karpathy, X, June 2025. https://x.com/karpathy/status/1937902205765607626 (quote from search snippets; not fetched; secondary).

4. **Karpathy: LLM wiki, with a schema file and a lint step.** The schema is "A document (e.g. CLAUDE.md for Claude Code or AGENTS.md for Codex) that tells the LLM how the wiki is structured, what the conventions are, and what workflows to follow"; "You and the LLM co-evolve this over time". Lint: "Periodically, ask the LLM to health-check the wiki. Look for: contradictions between pages, stale claims that newer sources have superseded, orphan pages with no inbound links." Why wikis die: "Humans abandon wikis because the maintenance burden grows faster than the value." Karpathy, GitHub gist. https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f (primary). The human stays in charge of sourcing and the right questions.

5. **ACE names both failure modes of self-edited context.** Prior methods suffer from "brevity bias, which drops domain insights for concise summaries" and "context collapse, where iterative rewriting erodes details over time." Zhang et al. (Stanford, SambaNova, Berkeley), arXiv 2510.04618. https://arxiv.org/abs/2510.04618 (primary). Worked case: "at step 60 the context contained 18,282 tokens and achieved an accuracy of 66.7, but at the very next step it collapsed to just 122 tokens, with accuracy dropping to 57.1" (HTML version, https://arxiv.org/html/2510.04618).

6. **ACE remedy: delta updates, grow-and-refine, dedupe.** Contexts are "compact delta contexts: small sets of candidate bullets distilled by the Reflector and integrated by the Curator"; "bullets with new identifiers are appended, while existing bullets are updated in place"; a "de-duplication step then prunes redundancy by comparing bullets via semantic embeddings." It learns "without labeled supervision, instead leveraging execution feedback". Limits the authors admit: it needs a "reasonably strong Reflector" and "not all applications require rich or detailed contexts." Same paper. Reported gains: +10.6% on agent benchmarks, +8.6% on finance (abstract).

7. **Dynamic Cheatsheet: self-curated, concise, transferable memory.** The memory stores "accumulated strategies, code snippets, and general problem-solving insights", "self-curated, focusing on concise, transferable content rather than full transcripts." Suzgun, Yuksekgonul, Bianchi, Jurafsky, Zou, arXiv 2504.07952. https://arxiv.org/abs/2504.07952 (primary; quotes are fetch-tool paraphrase in part, so unverified as exact).

8. **Reflexion and Voyager: verbal lessons and reusable skills work, in tasks with a clear success signal.** "Reflexion agents verbally reflect on task feedback signals, then maintain their own reflective text in an episodic memory buffer" (91% pass@1 on HumanEval vs 80%). Shinn et al., https://arxiv.org/abs/2303.11366 (primary). Voyager keeps "a growing collection of executable code"; skills are "interpretable, and compositional, preventing catastrophic forgetting." Wang et al., https://arxiv.org/abs/2305.16291 (primary). Both rely on a hard pass/fail signal (tests, game state). Voyager skills are verified by self-check before they enter the library (from my knowledge of the paper; fetch did not quote it; unverified here).

9. **Breunig: four ways a long or messy context fails.** Poisoning: "When a hallucination or other error makes it into the context, where it is repeatedly referenced." Distraction: "When a context grows so long that the model over-focuses on the context." Confusion: "superfluous content in the context is used by the model to generate a low-quality response." Clash: "When you accrue new information and tools in your context that conflicts with other information in the context." Drew Breunig, https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html (primary). Fixes: pruning is "Removing irrelevant or otherwise unneeded information"; summarization is "easy to do, but hard to perfect" (https://www.dbreunig.com/2025/06/26/how-to-fix-your-context.html, primary).

10. **Chroma: length alone degrades output, even on easy tasks.** "model performance varies significantly as input length changes, even on simple tasks"; "models do not use their context uniformly; instead, their performance grows increasingly unreliable as input length grows"; "Even a single distractor reduces performance relative to the baseline... adding four distractors compounds this degradation further." Chroma Research, https://www.trychroma.com/research/context-rot (primary). Caveat: tests are on retrieval-style tasks, not on instruction files.

11. **LangChain: three memory kinds, and memory can go wrong.** "Procedural memories" are instructions that steer behavior; semantic memories are facts; episodic memories are examples. Reflection follows "each agent turn", as in Reflexion. A bad retrieval (ChatGPT put a user's location into an image) makes users feel their "context window no longer belongs to them." Harrison Chase / LangChain, https://www.langchain.com/blog/context-engineering-for-agents (primary; quotes are the fetch tool's paraphrase in part, so unverified as exact).

12. **Weng: context is a hard budget for agent instructions.** "The restricted context capacity limits the inclusion of historical information, detailed instructions, API call context, and responses." And "Self-reflection is a vital aspect that allows autonomous agents to improve iteratively by refining past action decisions and correcting previous mistakes." Lilian Weng, https://lilianweng.github.io/posts/2023-06-23-agent/ (primary).

13. **Empirical result on AGENTS.md files: most of them do not help.** "providing context files does not generally improve task success rates, while increasing inference cost by over 20% on average"; "instructions in the context files are well followed by coding agents" but "repository overviews... are not helpful"; context files need "rigorous evaluation before deployment." Gloaguen et al. (ETH Zurich, SRI Lab), arXiv 2602.11988. https://arxiv.org/abs/2602.11988 (primary). Search-snippet detail, not verified in the paper text: LLM-written files lower success 0.5 to 2%, human-written files raise it about 4%, and context files add 14 to 22% more reasoning tokens. Useful for us: non-standard, non-discoverable rules help; generic overviews do not.

14. **Counter-evidence: file size and layout may matter less than assumed.** McMillan ran 1,650 Claude Code sessions. "None of the four structural variables [size, position, architecture, contradictions] or three two-way interactions produces a detectable contrast after multiple-testing correction"; compliance fell about 5.6% per extra generated function. arXiv 2605.10039, https://arxiv.org/abs/2605.10039 (primary, fetch-tool summary). Caveat: one trivial target annotation; it does not show that large files are safe for hard rules.

15. **Hamel Husain and Shreya Shankar: look at data; criteria drift.** "The magic to find what's most important and really do anything with evals is to look at the data" (Husain, via a secondary interview summary, https://humanloop.com/blog/why-your-product-needs-evals, not fetched; unverified wording). "These unit tests are crucial to getting feedback quickly when iterating on your AI system (prompt engineering, improving RAG, etc.)" and prompt-only work plateaus as surface area grows (https://hamel.dev/blog/posts/evals/, primary). Shankar et al.: "users need criteria to grade outputs, but grading outputs helps users define criteria" (https://arxiv.org/abs/2404.12272, primary). So criteria for "good" also change, and a human must stay in the loop.

Not found or not verified: Simon Willison on self-editing instructions (he writes on AGENTS.md and skills as human-authored, e.g. https://simonwillison.net/2025/Oct/16/claude-skills/, only seen in search results); timestamps of Karpathy's "Software Is Changing (Again)" talk (not checked).

## Implications for a reflect loop that edits repo skills after each run (inference)

This section is inference from the findings. No source states these items as rules for this repo.

1. **Add only what a check or test-like signal shows.** Write a lesson when a run hit a concrete failure, the cause is known, and the agent could not find the answer from the code (finding 13: only non-discoverable rules pay off). Do not add repo overviews.
2. **One incident is one candidate, not a rule.** Record it in a backlog first. Promote to a skill after it repeats, or when one failure cost much (over-fitting guard; finding 9 poisoning: a wrong lesson is referenced again and again).
3. **Replace before you add.** First search the skills for the same topic. If a rule exists, edit it in place. If two rules clash, resolve them in the same commit (finding 9, clash; finding 4, lint for contradictions).
4. **Use small deltas, never a full rewrite by the model.** Each run changes a few bullets, with a stable ID or heading per rule (finding 6). A full rewrite invites context collapse and brevity bias (finding 5). A rare, human-approved rewrite for size is still fine, with a diff review that checks no rule was lost.
5. **Dedupe and merge on every pass.** The reflect step lists near-duplicate rules and merges them. Keep the failure mode, the tool name, and the exact command; these are the details brevity bias removes (finding 5).
6. **Budget.** Give every always-loaded file a hard line cap, and keep the rest in skills that load on demand (findings 10, 12). A new rule must delete or shorten something when the file is at its cap. Move long detail to a referenced file. Do not trust the McMillan result (finding 14) to lift the cap for hard rules.
7. **Prefer a check over a sentence.** If a rule can be a script, hook, or test, build that and delete the sentence. This matches the repo rule in AGENTS.md and Karpathy's point about moving knowledge from text toward habit (finding 2).
8. **Eval before you keep it.** For each changed rule, name the failure it targets, and replay that case (or the cheapest proxy) with and without the change. Keep it only if the failure goes away and a small regression set still passes (findings 13, 15). If no replay is possible, mark the rule "unverified" and review it again after the next runs.
9. **Human review of every skill change.** The change arrives as a normal PR diff. The reviewer checks for over-fitting, contradictions, and lost detail (findings 4, 15: criteria drift means judgement stays with people).
10. **Prune on a schedule.** Every N runs, run a lint pass: stale rules, rules the code now enforces, rules never cited in any run, orphan references (finding 4). Deleting a rule needs the same review as adding one.
11. **Keep the evidence trail.** Each rule links to the run or commit that caused it, so a later run can test whether the cause still exists (supports items 2 and 10).
